## 追加：老板举反例「纯纯写作就行」→ 对比取证，结论钉死

老板不服（"为什么别的 app 就可以，例如纯纯写作"）。设备上正好装了纯纯写作，做了**同条件对比取证**：

### 铁证：两边编辑器的"血统"不同
| | 编辑器类 | 父类 |
|---|---|---|
| 纯纯写作 | `com.drakeet.purewriter.rU` | **`android.widget.EditText`** ← 系统标准文本框的定制版 |
| 铁锈工坊（sora） | `io.github.rosemoe.sora.widget.CodeEditor` | **`android.view.View`** ← 纯自绘控件 |

- 纯纯写作：`adb pull com.drakeet.purewriter`（30MB）→ `dexdump ext/classes.dex | grep -B25 "Superclass.*widget/EditText"` 拿到子类清单；
  同时命中 `com/drakeet/purewriter/Gm;`、`com/drakeet/purewriter/rU;`。
- sora：`javap -classpath cls io.github.rosemoe.sora.widget.CodeEditor | head -3` → `extends android.view.View`。

### 系统侧判定方法也挖到了
`getServedViewType` **不在** `services.jar`（搜遍 3 个 dex 为 0），而在 **`/system/framework/framework.jar`**
的 `classes2.dex`，定义于 **`android.inputmethodservice.RemoteInputConnection`** 和
`android.inputmethodservice.IRemoteInputConnectionInvoker`。
→ `RemoteInputConnection` 是**输入法进程**里的类（包装 app 传来的 IInputConnection），它手里**没有 app 的 View 对象**
→ 说明"served view 类型"是系统在建立输入连接时算好带过来的，**判定依据是承载焦点的 View 的实际类型**
（系统只分「标准文本框 / 其他」，输入法再拿它二分：`df.c` 里 `==1` 走 TextView 型，否则走 WebView 型）。

### 最终结论（和上一轮一致，但这次证据完整）
**接不上。** 这不是代码写法问题，是**编辑器内核血统**问题：
- 系统只认「系统文本框(EditText/TextView)」和「网页(WebView)」两类输入框；
- sora 是 `extends View` 的自绘控件，系统不把它当输入框；
- **app 无法改变已编译库的继承链**，所以没有口子。
- 想让输入法认，只有换内核（用 EditText 系或 WebView 系重构编辑器）——**代价不可接受**。

### 顺带确认（可卖点）
`/system/framework/android/view/inputmethod/InputMethodManager_compat_config.xml` 是标准 AOSP 内容，无 vivo 定制。

### 教训
上一轮我凭"IME_FLAG_NO_EXTRACT_UI 会让候选栏消失"的旁证就下了结论，被实测打回。
这次靠**同条件对比（纯纯写作 vs 本 app）+ 系统侧方法定位**才钉死。**结论要落到"别人为什么行"的同一维度上比，别跨维度找解释。**

## 终局：判定源码拿到了（100% 确定）

链路：输入法 `df.c`（TouchBarManager）→ `RemoteInputConnection.getServedViewType()`（输入法进程）
→ `IRemoteInputConnectionInvoker`（Binder）→ **`RemoteInputConnectionImpl.getServedViewType()`（app 进程！）**

`/system/framework/framework.jar` → `classes4.dex` → `android.view.inputmethod.RemoteInputConnectionImpl`
（jadx `--single-class` 反编译）里的实现：

```java
private synthetic Integer lambda$getServedViewType$57(InputConnectionCommandHeader header) {
    if (header.mSessionId != this.mCurrentSessionId.get()) return 0;
    InputConnection ic = getInputConnection();
    if (ic == null || !isActive()) return 0;
    if (getServedView() != null && TextView.class.isAssignableFrom(getServedView().getClass())) {
        return 1;   // 标准文本框
    }
    return 2;       // 其他（输入法按 WebView 型处理 → 抓不到 → 提示不兼容）
}
```

**判定唯一依据：`TextView.class.isAssignableFrom(焦点 View 的类)`** —— 即"是不是继承自系统文本框"。

对照：
- 纯纯写作 `com.drakeet.purewriter.rU extends android.widget.EditText extends TextView` → **1** → 支持
- 铁锈工坊 `io.github.rosemoe.sora.widget.CodeEditor extends android.view.View` → **2** → 不支持

**`isAssignableFrom` 是真实继承关系，无法用任何 app 侧代码欺骗**（不是接口方法，不能 override，也不是可重写的 View API）。
**唯一出路是换编辑器内核（EditText 系派生）**——等于把语法高亮/补全/行号/符号栏全推倒重写，**代价不可接受**。

### 反编译链路（最终版，可复用）
1. 厂商 app：`adb pull` → `dexdump <dex> | grep -B25 "Superclass.*widget/EditText"` → 拿子类清单（判断"血统"最快）
2. 厂商输入法：`aapt2 dump resources base.apk | grep -B6 "<提示文案>"` → 资源名 → Python 回溯方法 → `jadx --single-class` 出源码
3. **系统侧**：`/system/framework/framework.jar`（**不用 root 就能 pull！**，`-rw-r--r--`）
   → 方法名不在就换 dex 搜（`classes2~6.dex` 逐个 `grep -a -c`）
   → `dexdump` 不带 `-d` 出结构（小、够用）+ Python 回溯类名 → `jadx --single-class <类> fw/classesN.dex`
   - 注意：`services.jar` 里**没有** IMMS 的 vivo 定制方法，加的 API 落在 `framework.jar`

## 第三轮：老板指出真正的问题 → 定位根因并修复

**老板原话**："无论撤销几次撤销按钮都是亮着的，但是点一次重做撤销按钮就灰了"

### 根因（javap 反编译 `UndoManager` 字节码核实）：**栈指针更新滞后于变更通知**

`UndoManager.undo(Content)` 的执行顺序：

```
16: putfield      ignoreModification:Z
29: actionStack.get(stackPointer)      // 取待撤销动作
40: ContentAction.undo(content)        // ★ 应用内容变更 → 触发 Content 通知 → 派发 ContentChangeEvent
45: getfield      stackPointer:I
50: putfield      stackPointer:I        // ★ 到这里才写回（慢一步）
```

`redo()` 完全同构（`ContentAction.redo(content)` 之后才 `stackPointer++`）。

→ **在 `ContentChangeEvent` 回调里读 `canUndo()/canRedo()`，拿到的是【变更前】的旧值。**

判定式（javap）：
- `canUndo() = isUndoEnabled() && stackPointer > 0`
- `canRedo() = isUndoEnabled() && stackPointer < actionStack.size()`

**逐帧验证与老板现象严丝合缝**：编辑 3 步 → 撤销 3 次，每次都读到"撤销前"的值（≥1）→ **一直亮**；
撤到底那次读到 1（仍 true）；**点重做时栈指针已是 0 → 读到 false → 按钮灰** ✓✓

### 第二层放大（项目侧）
`EditorScreen` 的 `EditorToolbarAction.REDO` 分支在 `editor.redo()` 后立即 `canUndo = editor.canUndo()`
（**这个值其实是对的**，因为 redo 已返回），但它**只改了局部状态、没上报宿主**（没调 `onCanUndoChange`），
而事件回调那次错误上报已经把宿主的 `editorCanUndo` 写成 false 了 → 顶部按钮灰。

### 为什么普通打字不受影响
`Content` 对插入 / 删除的通知顺序**相反** —— `UndoManager.afterInsert/afterDelete(...)`（更新栈指针）**先**，
之后才遍历 `ContentListener` 派发 `ContentChangeEvent`。
→ **只有 `isCausedByUndoManager` 这一支需要延后读。**

### 已修（2 处）
1. `SoraCodeEditor.kt` 的 `ContentChangeEvent` 回调：按 `event.isCausedByUndoManager` 分支，
   撤销 / 重做改用 `editor.post{}` **延后一帧**读 `canUndo()/canRedo()` 再上报；
   普通输入保持立即读 —— **打字热路径零额外开销**。
2. `EditorScreen.kt`：`UNDO` / `REDO` 分支去掉紧跟 `undo()/redo()` 的立即读取，统一交给回调上报。

编译 + `installDebug` 通过（`build_undo_fix.log`）。报告已更新（★ 条置顶，含字节码证据）。

### ⚠️ 教训（值得写进 MEMORY）
**sora 的「内容变更通知」与「撤销栈指针」不保证同步。** 凡是要在变更回调里读"能不能撤销 / 重做"
或任何由变更衍生的状态（`canUndo`/`canRedo`），**必须先确认 sora 是先更新状态还是先通知**；
撤销 / 重做这一支是"先通知后更新"，必须延后一拍读。

## 第四轮：#2「未保存标记不回落」已修复

**老板原话**："全部撤销完了按理来说就默认为没有更改了，但是保存按钮还是亮着的，返回还是会问我要不要保存"

**根因**（第三轮已查明）：sora 的 `Content`/`UndoManager` **无** `markSaved()`/`isModified()`（javap 核实过）；
项目侧 `onTextChange` 里 `isModified = true` **无条件置位**，只有保存成功才清 → 撤销回原样也不回落。

### 修法：引入「已保存基线」`savedSnapshot`

**1. `SoraCodeEditor.kt`**
- `EditorWorkspaceEntry` 加字段 `savedSnapshot: String = ""`
  （**必须随缓存一起走**，否则切文件 / 跨页面回来后撤销回原样无法熄灭）
- 新增参数 `onUndoRedoApplied: ((String) -> Unit)? = null`，在撤销 / 重做的 `post{}` 里
  （与 canUndo/canRedo 上报同一处）把最新文本报出去

**2. `EditorScreen.kt`**
- 新增 `var savedSnapshot by remember(filePath) { mutableStateOf("") }`
- **文件加载完成**（`contentLoaded = true` 之前，含加载失败路径）→ `savedSnapshot = text`
- **workspace 恢复** → `savedSnapshot = workspaceEntry.savedSnapshot`
- **保存成功**（`stillUnchanged` 判定处）→ `savedSnapshot = currentText`
  （**编辑器形态的内容**，不是反向翻译后的写盘内容）
- `onTextChange`：`isModified = if (it.length == savedSnapshot.length) it != savedSnapshot else true`
  —— **长度不同直接早退**，打字热路径无额外 O(n) 开销；这样**手动改回原样也能熄灭**
- `onUndoRedoApplied = { isModified = it != savedSnapshot }` —— 撤销 / 重做的最终判定

### ⚠️ 最关键的坑
快照必须是**编辑器形态**的内容（`currentText` / `latestEditorText`），
**绝不能**用写盘的 `contentToSave`（中英模式下它是反向翻译后的英文）—— 否则永远匹配不上。

编译 + `installDebug` 通过（`build_modified_fix.log`）。报告 #2 已标"已修"。

## 第五轮：首页模组简介「显示空白」排查（仅出方案，未改码）

**现象**：首页文件卡片显示的模组简介（description），若前几行是换行 / 字面 `\n` → 显示为空。

**根因（已定位到具体函数）**：`HomeScreen.kt:1848`

```kotlin
private fun readModInfoDescription(dir: File): String? =
    readModInfoValue(dir, "description")?.replace("\\n", "\n")
```

- `readModInfoValue`（`HomeScreen.kt:1816-1834`）里**已经**做了 `raw.trim()` + `takeIf { it.isNotBlank() }`，
  **但此时字面 `\n` 还只是两个普通字符（`\` + `n`），trim 对它们无效** → `"\n\n\n简介"` 原样通过、还被判定为"非空白"
- **之后**才执行 `replace("\\n", "\n")` → **前导凭空多出三个真换行**
- 首页 `Text(maxLines = 1)` 只渲染第一行 = 空行 → **看起来没内容**

**只有字面 `\n` 写法会踩**；`"""` 多行块（真换行）反而正常 —— 因为 `trim()` 能正常吃掉真换行。

**方案**：
- **A（推荐）**：清洗顺序前移 —— 先 `replace("\\n","\n")` 还原成真换行，再
  `lines() → map{trim} → filter{非空} → joinToString(" ")`，全空则返回 null。
  改动面：**仅该私有函数**（首页专用，不影响 `ModInfoScreen` 编辑页）。
  副作用：多行简介由"只显示第一行"变成"多行连成一行 + 省略号"（信息量更大，形态变化需老板点头）。
- **B（保守 1 行）**：`?.replace("\\n","\n")?.trim()` —— 只去前导空白，保证第一行有内容；中间空行行为不变。
- **C（不推荐）**：把 `maxLines` 改成 2/3 —— 前导空行会占掉行数，显示得更少。

**老板选择**："假设没有内容的话可不可以无视前面的换行直到有内容显示为止" —— 即**跳过前导空行直到第一个有内容的行**
（方案 A 的核心，但**不压成一行**，保留后续换行结构与"多行只显示第一行"的既有语义，比 A 更保守精确）。

**已实施**（`HomeScreen.kt:1848` 的 `readModInfoDescription`）：

```kotlin
readModInfoValue(dir, "description")
    ?.replace("\\n", "\n")
    ?.lines()
    ?.dropWhile { it.isBlank() }   // ★ 跳过前面所有空行（含只含空白的行）
    ?.joinToString("\n")
    ?.takeIf { it.isNotBlank() }
```

- **全空 → 返回 null → 那一行整块不显示**（比显示一块空白更好）
- 真换行 / `"""` 多行块写法原本就正常（`readModInfoValue` 里的 `trimStart()` + `trim()` 已把真换行吃掉），
  加 `dropWhile` 对它们无副作用
- **只动首页私有函数，不影响 `ModInfoScreen` 编辑页**

编译 + `installDebug`（`build_desc_fix.log`）。
