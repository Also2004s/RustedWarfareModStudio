## 修复：保存显示「已保存」，返回目录重开修改消失

### 根因（两条，代码已坐实）
1. **翻译缓存盖戳时机错**：`SearchTranslationCache` 先读原文、再翻译、**翻译完才取 mtime/size 盖戳**。翻译窗口内（`translateToChinese` 十几~几十 ms）若发生保存写盘，缓存就变成「旧译文 + 新时间戳」→ 之后每次判定都「新鲜」→ 重开显示旧内容，且污染持久化在 `index.json`，不是刷新页面能自愈。
   - 触发路径是日常节奏：保存 → 继续改 → 停手 250ms 触发继承链解析（未命中→读盘+翻译，窗口开启）→ 窗口内再保存一次。
   - 文件越大、连点保存越频繁，概率越高（与「有概率」吻合）。
   - 关键认知：**保存后缓存记录必然过期**，所以「保存→继续编辑」几乎必然触发一次重译，窗口常态化。
2. **保存不刷新中文缓存**：`saveSync` 全程不碰缓存（全文件只有加载时两处读取）。后果 = 重开必重译（慢）+ 上条窗口的主要入口。

### 修法（只改这两处 + 同一缺陷的兜底落盘点）
- `SearchTranslationCache.getChineseContent` / `putCacheSync`：快照改成**读原文之前**取（先取戳后读文本 = 宁多译一次，绝不记错版本）。`putCacheSync` 签名改 `(file, chineseContent, srcMtime, srcSize)` 强制调用方传快照；唯一调用方 `InheritanceResolver.readFileContent` 同步改。
- 新增 `SearchTranslationCache.invalidate(file)`：移除索引 + 内存项，下次必重译（不删缓存文件，重译按同路径覆盖）。
- `EditorScreen.saveSync` 写盘后同步缓存：中文视图（`needReverseTranslate`）→ `putCacheSync(currentText, 保存后的 mtime/size)`；英文视图 → `invalidate`（手上没有可靠中文版本，绝不留旧记录）。
- `MainApp.saveWorkspaceEntry`（兜底/暂存落盘）同样处理 —— 它写同一批文件，漏掉等于没修完。
- 全程 try-catch 包住缓存同步，缓存失败不影响保存结果（缓存是附属品）。

### 判定 / 未修
- 第 3 条（“只比 mtime 不比 size”，`readCacheSync:209`、内存命中 `:202/:231`）：真实但只在外置 SD/FAT（约 2 秒精度）且同长度修改时触发；且 **size 校验救不了污染**（污染的 size 也是新的）。老板批准范围内**未修**。
- 第 4 条（`loading` 时静默 `onSaved(true)`）：无实际危害（加载期无改动可丢，且空内容保护会拒绝覆盖）。**未修**。
- 我上一轮给的判据「切英文视图能看到新内容」是**错的**：切语言会基于当前显示内容重新翻译（`EditorScreen:1584-1600`），两个视图一样旧。正确判据 = 「近期修改」页里该文件的保存记录（记录的是真实写盘内容）。

### 验证
- `compileDebugKotlin` 通过；`testDebugUnitTest` 350 个 2 红，红的就是既有两条（`CompletionSymbolsTest`、`CustomCompletionsFormatTest`），无新增失败。
- 修复后：任何写盘点都不再可能产生「幽灵旧版」（戳永远 ≤ 实际内容版本，最坏是多译一次）；保存后重开也不再重译。
- 残留风险（未处理，架构约定）：`putCacheSync` 的缓存文件是直接 `writeText`（老板定的“可再生缓存不走原子写”），启动预热与保存路径理论上可能并写同一缓存文件。
