## 查重变慢根因 + 修复（06:11，老板实测：开了多线程还变慢）

- **根因**：第一轮保存链路修复给 `AtomicWrite` 加的是**全局单一锁**（WRITE_LOCK），把所有文件写盘串行化。查重/翻译缓存预热是多线程并行写**各自不同的输出文件**，被全局锁排队 → 性能退化。
- **修复**：`AtomicWrite.atomicWriteText` 全局锁 → **per-path 锁**（ConcurrentHashMap<absolutePath, Any>）：同一路径才串行（防固定 $name.tmp 并发截断拼乱码），不同路径并行。锁对象不 remove（remove 会引入新锁对象与等待旧锁线程并行的窗口）。编译通过。
- **受益场景**：查重多线程、翻译缓存并行预热、继承链预热、多文件保存。
- **教训**：全局锁防损坏要看清范围——"同一路径"才是必要的串行范围，"不同路径"是并行窗口，一刀切全局锁会牺牲并行性能。

- TranslationDedupChecker：outFile.atomicWriteText → writeText
- SearchTranslationCache / InheritanceCache：缓存文件 atomicWriteText → writeText（**索引保留原子写**——低频且防撕裂）

**教训（记长期笔记）**：原子写只用于「用户数据」（编辑的文件/设置/历史/待办）；「可再生的缓存/输出」（翻译缓存/继承缓存/查重输出/补全表）用直接写——损坏了重新生成即可，原子写的高开销会拖垮多线程。
**GitHub 是超级旧版**：git diff 对比 GitHub 无意义（含大量非本对话改动），判断"谁改的"只能靠 38 点清单+代码调用链。

## 查重慢的结构性根因 + 优化（09:19，老板："缓存修复了，查重没修复"）

- **根因**：缓存预热是**整文件翻译一次**（translateToChinese）；查重是**每行调 translateToEnglish**——每次走完整 processLines 状态机的固定开销（List 创建/joinToString/正则对象），大文件几百行时固定开销放大几百倍。多线程只能并行文件级，救不了每行的固定开销。
- **优化**：查重 checkOneFile 改为**整文件翻译一次**（translateToEnglish(content)），translatedLines 按行索引对齐对比（processLines 保持行数：多行字符串按原始行还原 L409-421）。性能大幅提升，且多行字符串处理比逐行更准确。编译通过。
- **教训**：批量逐行调翻译引擎 = N 倍固定开销；能用一次调用处理的绝不分 N 次。查重与缓存的差异就在这。
