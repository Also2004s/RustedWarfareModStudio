## P0-1 外部 Intent 打开文件时未保存修改可能丢失

**现状（before，真实代码）** — `MainApp.kt`：

```kotlin
// 消费 MainActivity 从外部 intent 传入的待打开文件
LaunchedEffect(Unit) {
    MainActivity.pendingOpenFile?.let { (name, path) ->
        selectedFile = name to path
        browserStartPath = File(path).parentFile?.absolutePath ?: ""
        currentScreen = Screen.EDITOR
        MainActivity.pendingOpenFile = null
    }
}
```

**影响案例（前后对比）**：
- **before**：正在编辑 `unit.ini`（有未保存修改）→ 系统文件管理器里"用铁锈工坊打开" `map.ini` → 直接切文件，`unit.ini` 的修改丢失。`autoSave` 关闭时必丢；开启时依赖 `onPause` 兜底，不保证。
- **after**：消费前检查当前是否在编辑器且有无保存修改，先保存或弹确认对话框（复用已有 `showEditorBackDialog` 模式）。

**优化方案（after）**：

```kotlin
LaunchedEffect(Unit) {
    MainActivity.pendingOpenFile?.let { (name, path) ->
        if (currentScreen == Screen.EDITOR && editorTextHolder.text.isNotEmpty()) {
            if (SettingsManager.autoSave) editorSaveTrigger++   // 先落盘再切换
            else { MainActivity.pendingOpenFile = null; showEditorBackDialog = true; return@let }
        }
        selectedFile = name to path
        browserStartPath = File(path).parentFile?.absolutePath ?: ""
        currentScreen = Screen.EDITOR
        MainActivity.pendingOpenFile = null
    }
}
```

**验收**：开/关自动保存各测一次：编辑 A.ini → 外部打开 B.ini → 返回后 A.ini 修改仍在（保存或取消后丢弃是用户确认过的）。

## P1-2 值补全每次按键全文扫描

**现状（before，真实代码）** — `CompletionProvider.kt`：`getCompletions()` 触发值补全时，每次按键都调用：

```kotlin
val memoryNames = extractMemoryNames(textBeforeCursor)          // 全文 split + 2 个正则
val (tags, globalTags, resources, globalResources, unitNames) =
    extractProjectSymbols(textBeforeCursor)                     // 全文 split('\n') + 6 个正则逐行匹配
```

**实测数据（JVM 复刻，主线程）**：

| 文件规模 | 符号扫描 | memory 扫描 | 合计/次按键 |
|---|---|---|---|
| 0.2MB（1 万行） | 13.1 ms | 2.8 ms | ≈ 16 ms |
| 1.0MB（5 万行） | 23.2 ms | 9.9 ms | ≈ 33 ms |
| 3.9MB（20 万行） | 64.3 ms | 33.0 ms | ≈ 97 ms |

**影响案例（前后对比）**：
- **before**：在 20 万行的大型 mod 文件里输入 `属性名:` 触发值补全，每次按键 UI 卡约 100ms，输入明显不跟手。
- **after**：文件加载后 + 文本变化 debounce(250ms) 时在后台提取一次符号集并缓存，按键时直接读缓存，**0ms**（纯内存读）。

**优化方案（after，设计）** — 复用节名解析的模式：

```kotlin
// EditorScreen.kt：新增文件级符号缓存
var fileSymbols by remember(filePath) { mutableStateOf(ProjectTagInfo.EMPTY) }
LaunchedEffect(filePath) {
    snapshotFlow { text }
        .debounce(250)
        .collect { t -> fileSymbols = withContext(Dispatchers.Default) { extractSymbols(t) } }
}
// CompletionProvider：getCompletions(..., cachedSymbols: ProjectTagInfo = EMPTY)
//   内部不再扫全文，直接合并 cachedSymbols + 项目级 ProjectTagScanner 缓存
```

**验收**：20 万行文件输入补全无卡顿；benchmark 复测 after 路径耗时 ≈ 0ms。

## P1-3 近期修改弹窗主线程读历史 + 算 diff

**现状（before，真实代码）** — `MainApp.kt`：

```kotlin
// 打开历史弹窗时，在 composition 里同步读盘 + 解析 JSON
val history = remember(path) { SaveHistoryManager.getHistoryForFile(context, path) }
val allFiles = remember { SaveHistoryManager.getRecentFiles(context) }
// DiffView 中主线程算 LCS diff
val ops = remember(before, after) { computeLineDiff(before.lines(), after.lines()).filter { it.type != ' ' } }
// 确认/回退按钮直接主线程写盘
SaveHistoryManager.updateBaseline(context, path, newBaseline)
SaveHistoryManager.confirmFile(context, path)
```

**实测数据（JVM 复刻，主线程）**：

| 文件行数 | 算法分支 | 单次 diff 耗时 |
|---|---|---|
| 500 | LCS-DP | 34 ms |
| 1000 | LCS-DP | 137 ms |
| 1500 | LCS-DP | 277 ms |
| 2000 | LCS-DP | 480 ms |
| ≥2100 | 位置配对（退化） | 0.2~0.5 ms |

> 注意：≥2100 行虽快，但走退化分支，**差异质量下降**（按行号配对，插入/删除会误判后续行）。

**影响案例（前后对比）**：
- **before**：历史里有 1500 行文件，打开"近期修改"弹窗 + 展开 diff 卡约 300ms；多次保存后 `save_history.json` 数 MB，打开弹窗同步解析卡顿明显。
- **after**：读历史与算 diff 全部异步（`LaunchedEffect` + `Dispatchers.IO/Default`），加载中显示进度，UI 不阻塞。

**优化方案（after，设计）**：

```kotlin
// RecentFilesDialog
var history by remember(path) { mutableStateOf<List<SaveRecord>>(emptyList()) }
var loading by remember(path) { mutableStateOf(true) }
LaunchedEffect(path) {
    history = withContext(Dispatchers.IO) { SaveHistoryManager.getHistoryForFile(context, path) }
    loading = false
}
// DiffView
var ops by remember(before, after) { mutableStateOf<List<DiffOp>>(emptyList()) }
LaunchedEffect(before, after) {
    ops = withContext(Dispatchers.Default) { computeLineDiff(before.lines(), after.lines()) }.filter { it.type != ' ' }
}
```

**验收**：历史含 2000 行文件的场景，打开弹窗 / 展开 diff 不卡；UI 先出骨架/进度再出结果。

## P2-4 首页 mod 列表主线程解码大图

**现状（before，真实代码）** — `IniImageReader.kt`（`HomeScreen.kt:1156` 主线程调用）：

```kotlin
fun getImageForFile(file: File): ImageBitmap? {
    val content = file.readText(Charsets.UTF_8)          // 同步读整个 INI
    // ... 解析 image: 引用 ...
    val bitmap = BitmapFactory.decodeFile(imageFile.absolutePath)  // 原图全尺寸解码
}
```

**影响案例（前后对比）**：
- **before**：首页展示 10 个 mod，每个都同步读 INI + 原图全尺寸解码。一张 4000×3000 图解码后约 **32MB** 内存，列表滚动时卡顿 + 内存峰值高。
- **after**：解码移 `Dispatchers.IO`，按目标缩略图尺寸计算 `inSampleSize` 采样（如 4 → 内存降 16 倍，约 2MB/张），并用 `LruCache<String, Bitmap>` 缓存。

**优化方案（after，设计）**：

```kotlin
// IniImageReader.kt
suspend fun getImageForFile(file: File): ImageBitmap? = withContext(Dispatchers.IO) {
    // ...解析 image: 引用...
    val opts = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeFile(path, opts)
    val sample = calculateInSampleSize(opts.outWidth, opts.outHeight, THUMB_W, THUMB_H)
    BitmapFactory.decodeFile(path, BitmapFactory.Options().apply { inSampleSize = sample })
}
// HomeScreen.kt: LaunchedEffect(file) { iniImage = IniImageReader.getImageForFile(file) }
```

**验收**：首页 10+ mod 滚动流畅；用 `dumpsys meminfo` 对比解码内存峰值下降。

## P2-5 `saveSync` 里 `runBlocking(Dispatchers.Main)`

**现状（before，真实代码）** — `EditorScreen.kt:362`：

```kotlin
suspend fun saveSync(caller: String = "unknown"): Boolean = withContext(Dispatchers.IO) {
    ...
    // 优先读取编辑器实际内容，避免状态同步延迟导致保存旧内容
    val currentText = runBlocking(Dispatchers.Main) { editorRef?.text?.toString() } ?: text
```

**影响案例（前后对比）**：
- **before**：IO 线程 `runBlocking(Main)` 等待主线程返回编辑器内容。主线程繁忙（重组/动画/大文件渲染）时保存被拖慢，且 `runBlocking` 是反模式，易引入意外死锁。
- **after**：由 `onTextChange` 同步维护最新文本字段，保存直接读内存，无跨线程等待。

**优化方案（after，设计）**：

```kotlin
// EditorScreen.kt
var latestEditorText by remember(filePath) { mutableStateOf("") }
// onTextChange 回调（编辑器每次变化都会触发）里：latestEditorText = it
suspend fun saveSync(caller: String = "unknown"): Boolean = withContext(Dispatchers.IO) {
    val currentText = latestEditorText.ifEmpty { text }
    ...
}
```

**验收**：保存大文件不阻塞主线程；连续保存 20 次无异常；`runBlocking` 从代码中消失。

## P3-6 空 catch 静默吞异常

**现状（before，真实数据）**：`catch (_: Exception) {}` 约 **50 处**，分布：`HomeScreen` 12、`CustomCompletionsScreen` 10、`SearchTranslationCache` 7、`TranslationDict` 5、`InheritanceResolver` 4、`SoraCodeEditor` 4 等。

**影响案例（前后对比）**：
- **before**：`SearchTranslationCache` 写缓存失败 → 静默，用户感觉"翻译缓存不生效"，无日志可查。
- **after**：关键路径至少 `Log.w(TAG, "...", e)`；用户触发的保存/导入/查重失败给 Toast 提示。

**优化方案（after）**：逐文件把静默 catch 改为 `Log.w/e`；用户操作路径补 Toast。示例：

```kotlin
// before
try { file.writeText(...) } catch (_: Exception) {}
// after
try { file.writeText(...) } catch (e: Exception) {
    Log.w(TAG, "写入失败", e)
    // 用户操作路径：Toast.makeText(context, "保存失败", Toast.LENGTH_SHORT).show()
}
```
