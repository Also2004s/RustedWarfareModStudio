日期：2026-09-23　状态：**方案已批复并落地**（第三节是批复的方案原样保留，第六节是落地记录）

---

## 一句话结论

1. **「提前断行」不是手机问题、也不是字体问题，是我们自己那条断行规则造成的。**
   现在的断行不是"能塞多满塞多满"，而是**先给符号排座次**（括号组 → and/or → 加减乘除 → 逗号），轮到某一档时，只要这一档里有放得下的位置就断在那儿，**比它更靠右的位置哪怕还空着一大片也不会再看**（"档"有绝对优先权）。结果就是屏幕上明明还剩半行空白，它却在半路换行了。
2. 拿你给的那句实际算过：同一行宽度下，**有一行只用了 12 个字的宽度就换行，右边空了 48 个单位（≈24 个汉字）**；换成"先按结构分段、段内放满再换"，这一行能放满 60 个单位再换，**同样内容从 6 行缩到 5 行**。
3. 另外有两个"看起来还差一点点"的余量是编辑器底层原生行为（不是这个功能带来的）：量宽度按"最粗最斜"的字形估，和右侧固定留一个字符宽。合起来就是"还能放一个字却断了"的感觉。
4. 优化方案见第三节，**有 3 个点需要你拍板**（第四节）。不拍也按推荐值做也行。

## 一、「提前断行」是怎么回事

### 为什么

断行挑位置的方式，现在是"按符号类别分成四档，档有绝对优先权"：

| 档次 | 位置 | 说明 |
|---|---|---|
| 1 | 带 and/or 的括号组之前 | 整组搬到新行 |
| 2 | `and` / `or` 之前 | |
| 3 | `+` `-` `*` `/` 之前 | |
| 4 | `,` 之前 | **排最后** |

挑的时候从第 1 档开始：这一档只要有"放得下"的位置，就取最靠右的那个断行，**后面几档即使能放得更满也不再考虑**。

打个比方：像排队上车，排在前面的队伍只要有一个人能上就先上他，后面队伍即便能塞下三个人也不许上——车没坐满就开走了。

### 你在手机上看到的

- 一行里还剩一大截空白（甚至半屏），却已经换到下一行了；
- 越长的表达式（`+` `/` `,` 混在一起）越容易碰到；
- 用你那句 `,资源名=敌人=(…), 队友=(…), 队伍=max(…)` 实测（按一行 60 个单位算）：

| 现在断出来的行 | 用掉宽度 | 行尾留白 |
|---|---|---|
| `,资源名=敌人=(全局检查第一个单位` | 32 | 28 |
| `(需标签='I').敌人有此单位数量(需标签="I"))` | 42 | 18 |
| `, 队友=(全局检查第一个单位(需标签='I').队伍中此单位数量` | 55 | 5 |
| **`(需标签="I")`** | **12** | **48** ← 问题行 |
| `+全局检查第一个单位(需标签='I').盟友有此单位数量` | 48 | 12 |
| `(需标签="I")), 队伍=max(自身资源.敌人/自身资源.队友, 1)` | 55 | 5 |

问题行后面紧跟的 `+全局检查第一个单位` 其实完全放得下（12 + 19 = 31 ≤ 60），但因为 `+` 属于第 3 档、而这一档后面已经没有放得下的位置，就草草断在第 3 档那个 `+` 上了。

### 改之后会怎样

- 行尾不再出现大片浪费，同样内容行数更少（那句例子 6 行 → 5 行）；
- 断行落在结构分界处（顶层逗号 / and·or / 括号组），看起来像手工排的版。

### 还有一个附带现象：逗号被排在最末档

你那句里最想断的地方恰恰是 `,`（条目分界），但它被排在第 4 档（最低）。只要前面三档随便有一处放得下，就轮不到逗号。**这是设计上的错位，也是方案要改的重点之一。**

## 二、两个"差一个字"的余量（编辑器底层自带，不是这个功能引入的）

| 现象 | 为什么 | 影响 |
|---|---|---|
| 明明还能放一个字却断了 | 量行宽时故意按"最粗＋斜体"的字形估算（怕有加粗内容被挡在外面），估出来比实际显示宽 | 边界处约 1 个字符宽 |
| 右侧总留一丝空隙 | 行宽里固定扣掉一个字符宽（给光标留位置） | 同上 |
| 开了「软换行提示符」后可用宽度更窄 | 左侧要留标记位，左右各扣一次 | 关掉它一行能多放 1 个字符 |

这三条是原生行为，列出来是为了让你分辨"你说的提前断行"到底是哪一种。**第一条第二条无论开不开智能换行都存在；只有第三节说的那种"半屏留白式提前断行"是本功能引入的。**

## 三、优化方案（针对 `,资源名=` 这类表达式）

### 主干：从"符号排座次"改成"先分块、再填满"

**第一步 · 分块（结构优先）**
把下面这些位置定为**块边界**：

- 行首那一层的 `,`（条目分界，你例子里 `, 队友=` `, 队伍=` 就是这种）；
- 行首那一层的 `and` / `or`（条件分界）；
- 带 `and`/`or` 的括号组之前（整组搬走）。

换行时**先看能不能多装下一个完整的块**：能装就装，装不下就在块边界断。

**第二步 · 填满（块内）**
如果一个块本身比一行还长（比如 `, 队友=(…)` 那一段），这时候不再"排座次"，而是在块内部**取最靠右能放下的位置**断（加减乘除、括号、空格都算数），把这一行尽量填满。

**第三步 · 括号参数组整体搬**
`(需标签='I')`、`(冷却=30)` 这种挂在函数后面的参数括号整组一起走，不拆开。

### 效果对比（用你那句实测，行宽按 60 估算）

| | 现在 | 建议 |
|---|---|---|
| 行数 | 6 行 | 5 行 |
| 最浪费的一行 | `(需标签="I")`，只用 12/60，留白 48 | 用满 60/60 |
| 断行依据 | 符号类型排座次 | 结构分界 + 段内填满 |

### 建议保留不动的部分

- `=` 两侧不断（避免 `范围内` / `=200` 这种割裂）；
- `.` 只在其它位置都放不下时才用（避免 `.resource` 跑到行首）；
- 字面 `\n` 强制断行（`\n` 显示在新行行首）；
- 汉字不拆开（不把一个词从中劈开）。

### 可选加强（要不要你定，默认不做）

- **续行缩进**：换行后的内容缩 2 格、或对齐到所在括号。层次更清楚，代价是每行可用宽度少 2 格。
- **运算符号断行后单独成行首**：现在就是这样，保持。

### 现状算法（`breakLine` 主循环）

```
limit = 下一个字面 \n 的位置（无则行尾）      // R1 硬断
若 [rowStart, limit) 整体放得下 → 单独成行
否则：
  chosen = farthestFitting(parenGroups) ?: farthestFitting(andOr)
           ?: farthestFitting(operators) ?: farthestFitting(commas)
  若 chosen < 0：
     兜底一 主标点（含空格、'('，排除 '=' 相邻与汉字内部）
     兜底二 '.'（computeDotBreaks）
     兜底三 cjkSafeBreak（二分找最远放得下，避开 '=' 相邻与汉字内部）
rowStart = chosen
```

`farthestFitting` 遍历该档升序断点，`w([rowStart,p)) ≤ width` 则更新 `lastFit`，否则 `break`（依赖断点升序的单调性）。**跨档不回头**：高档只要有放得下的就锁死，这正是行尾留白的成因。

### 原版对照（javap 核实）

- sora 0.24.6 的 `WordwrapLayout.breakLine` 直接 `TextRow.breakText(width, antiWordBreaking)` 取 `WordwrapRow.startColumn/endColumn` 作为区域边界 —— **即"按测量填满"**，没有档位概念。
- 原版宽度公式与本项目一致：`width = editor.getWidth() - (int)(editor.measureTextRegionOffset() + paint.measureText("a")) - (int)miniGraphWidth * 2`。
- 测量用的 span 是 `SpanFactory.obtainNoExt(0, TextStyle.makeStyle(0,0,true,true,false))`（粗体+斜体，即最宽形态）—— 这是"差一个字"的来源之一，原版即如此。
- `CodeEditor.antiWordBreaking` 未在项目任何位置设置；javap 显示 `putfield antiWordBreaking` 只出现在 `setWordwrap(boolean,boolean,boolean)` 里，`<init>` 无显式赋值 → **默认 false**（词中可折行）。
- 该功能唯一的 UI 开关：`SettingsManager.smartWrap` / `autoWrap` / `wrapIndicatorEnabled`（设置页 `SettingsScreen.kt` "智能换行（逻辑断点）"）。

### 建议算法（伪码，实现时按此落地）

```
分析行 → 计算每个断点的 depth（进入该位置时的括号嵌套层数）
blocks = { depth==0 的 ',' } ∪ { depth==0 的 and/or } ∪ { 含 and/or 的括号组的 '(' }
inner  = 运算符(+ - * /) ∪ 其余 ',' ∪ 兜底标点(含空格)
while rowStart < len:
    若 [rowStart, len) 放得下 → 成行，结束
    b = 最远的、放得下的 blocks 断点
    若 b 存在 → 断在 b                // 块边界优先，允许块装不下时的留白
    否则 f = 最远的、放得下的 inner 断点 → 断在 f   // 块内填满
    否则 → cjkSafeBreak
```

要点与风险：

- `farthestFitting` 的 `break` 依赖升序单调，`blocks`/`inner` 必须保证升序去重（沿用 `sortedSetOf` + `clean()`）。
- `depth` 用一次线性扫描记录前缀深度即可，勿每次重算（行内 O(n²) 在长行上会拖慢布局线程）。
- 逗号归行尾 = 断点位置取 `,` 后第一个非空白字符处（连带其后空格一起留在上一行；若已到行尾则退回 `,` 本身）。
- 括号参数组整体化 = 计算括号匹配后，把"紧跟标识符的 `(` ... 匹配 `)`"整段视为不可拆区间（除非该区间自身宽度 > width）。
- 单测：`priorityBreaksGroupedByPriority`、`commaBreaksBeforeSymbol`、`sampleConditionalContainsExpectedBreaks` 需要按新顺序重写；`computePreferredBreaks`（兼容 API）保留。
- 不改 `SmartWrapCodeEditor` / 布局接口，只改 `SmartWrapBreaks` 的输出结构与 `breakLine` 的选取顺序；开关语义不变（关掉智能换行 = 原版 `WordwrapLayout`，无回归面）。
- 性能：多一次 `depth` 扫描 + 每行多几次 `breakText` 试探；现有 `farthestFitting` 已有早停，实测点在长行（>500 字符）滚动时的掉帧情况。

## 八、逗号换行消失的根因与修复（2026-09-23 老板追问「资源名换行呢？哪里去了」）

### 现象

七节回退后老板反馈：`资源名=..., 资源名=...` 这种地方**看不到逗号处换行了**。

### 根因（有量化数据）

七节版里逗号是**最低档**：`括号组 > and/or > 运算符 > 逗号`。布局层是「逐档试、`farthestFitting` 一命中就停」，所以**只要这一行里有一个运算符放得下，逗号档永远轮不到**。

`.workbuddy/tmp/wrap_revert.py`（等宽近似 汉字=2）实测老板样例：

| 项 | 位置（字符 index） | 宽度位置（单位） |
|---|---|---|
| 括号外逗号（逗号后） | 48 / 128 | **76 / 204** |
| 运算符 `+` `/` | 88 / 142 | — |

- 行宽 60 / 46 / 40：运算符（88 处段宽 70）放不下 → 逗号档命中 → 逗号留行尾 ✓（七节验证到的效果）
- **行宽 ≥ 70：运算符（88）放得下 → 运算符档抢先 → 逗号换行消失**

老板的编辑区行宽落在后者，所以"资源名处换行"看不见。

### 修法：只动次序，不动结构

把**括号外的逗号**从最低档提到运算符**之前**，括号内的逗号保持最低：

```
括号组 > and/or > 括号外逗号 > 运算符 > 括号内逗号
```

- 括号外逗号 = `资源名=..., 队友=...` 这类列表分隔（老板要的"资源名换行"）；
- 括号内逗号 = `max(a, b)` 参数分隔，仍不与运算符抢位置（否则 `自身资源.敌人/自身资源.队友, 1` 会断在逗号后而不是 `/` 前）。

| 文件 | 改动 |
|---|---|
| `editor/SmartWrapBreaks.kt` | `PriorityBreaks.commas` 拆成 `outerCommas`（depth==0，高档）+ `innerCommas`（depth>0，最低档）；新增 `depth` 数组；`computePreferredBreaks` 同步 |
| `io/github/rosemoe/sora/widget/layout/SmartWordwrapLayout.java` | 多取两档，在选择链里插入 `outerCommas`（在 `operators` 之前），新增 `oci` / `ici` 两个推进指针；四档选择的整体结构不变 |
| `test/.../SmartWrapBreaksTest.kt` | `priorityBreaksGroupedByPriority` 改用 `outerCommas`；新增 `outerCommaOutranksOperatorWhileInnerCommaDoesNot` |

### 效果（`.workbuddy/tmp/wrap_new.py`）

行宽 100（老板场景）：

| | 命中档位 | 第 3 行结尾 | 第 4 行 |
|---|---|---|---|
| 旧四档 | 运算符 142 | `…(需标签="I")), 队伍=max(自身资源.敌人` | `/自身资源.队友, 1)` |
| **新五档** | 括号外逗号 128 | `…(需标签="I")), ` | `队伍=max(自身资源.敌人/自身资源.队友, 1)` |

行宽 76 及以下两者一致（运算符本来也放不下，逗号档照样命中）。

### 代价

断点选在逗号处后，该行留白会比"填满式"多一些（行宽 100 时 15 → 37 单位）—— 因为**逗号位置必然比它后面的运算符位置靠前**，这是"资源名处换行"的固有取舍。
