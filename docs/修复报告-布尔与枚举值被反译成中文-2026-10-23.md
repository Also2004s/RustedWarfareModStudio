# 问题一：保存时英文值被反向翻成中文

## 为什么会这样

编辑器手里有两本账：**盘上那本英文原稿**，和**你眼前这本中文译稿**。保存时它按「中文 → 英文」把眼前这本翻回去，覆盖原稿。

它默认了一件事：**「你眼前这本里，所有值都该是中文」**。

可你粘贴进来的是英文。它看到 `true`，没有「这本来就是英文、不用动」的判断，直接拿 `true` 去查「中文对应的英文是什么」。

问题在于那本值对照表是**双向登记**的——`true` 和「真」写在同一条上，同时供两个方向查。于是它按「查中文」的路子去查 `true`，表把同一条的另一个方向递了回来：**`真`**。

一句话：**它在用「中文→英文」的规矩，去翻一段英文。** 越翻越回去了。

## 修复前的表现

### 你遇到的（保存历史实证）

新增的 `[action_悬崖减速显示]` 那一段，三行新粘进去的布尔值全部落盘成「真」：

```
isLocked:真
isAlsoViewableByAllies:真
isAlsoViewableByEnemies:真
```

而文件里原有的几十处 `true`（`hidden:true`、`isLocked:true`、`canAttack:false`…）**一个都没坏**。

分水岭不在属性名，在**内容来源**：原有的行你眼前看到的是「真」（打开文件时已经被翻成中文），保存时「真」→ `true` 正常；新粘的行你眼前看到的是 `true`，于是被反向翻成了「真」。

### 端到端复现（按 App 真实流程跑的）

打开英文原文 → 翻成中文视图 → 追加你粘贴的那段 → 保存：

| 行 | 中文视图里显示 | 保存后落盘 |
|---|---|---|
| 原有 `isLocked:true` | `锁定:真` | `isLocked:true` ✅ |
| 原有 `autoTrigger:true` | `自动触发:真` | `autoTrigger:true` ✅ |
| 原有 `movementType:LAND` | `运动类型:陆地` | `movementType:LAND` ✅ |
| **粘贴 `isLocked:true`** | `isLocked:true`（没人翻它） | **`isLocked:真`** ❌ |
| **粘贴 `isAlsoViewableByAllies:true`** | 同上 | **`isAlsoViewableByAllies:真`** ❌ |
| **粘贴 `isAlsoViewableByEnemies:true`** | 同上 | **`isAlsoViewableByEnemies:真`** ❌ |

### 为什么会让你觉得「有概率」

错的不是某一行，而是「中文视图里出现了英文形态的值」这件事。所以：

- 正常打开 → 全是中文形态 → **永远不出错**
- 粘一段英文进去 → **那一段必然出错**，段落里几个值就坏几个
- 冷启动抢时间（引擎没就绪时打开文件，界面拿到的是英文原文却仍按中文视图处理）→ **整篇的特殊值一次性全坏**

所以你感觉是随机，其实是「这次操作有没有把英文塞进中文视图」。

### 影响清单（不止布尔）

值表里的英文值一共 **9 个**，全部会中招：

| 文件里的值 | 保存后被写成 | 后果 |
|---|---|---|
| `true` / `false` | 真 / 假 | 布尔判断失效 |
| `LAND` | 陆地 | 移动类型读不出 |
| `WATER` | 水面 | 同上 |
| `HOVER` | 两栖 | 同上 |
| `AIR` | 空中 | 同上 |
| `OVER_CLIFF` | 跨悬崖 | 同上 |
| `OVER_CLIFF_WATER` | 跨悬崖和水面 | 同上 |
| `NONE` | 无 | 音效/射弹引用失效 |

`AUTO` 侥幸没事（值表里没登记它）；`TRUE` / `False` 这类大小写混写也侥幸没事（值表只登记小写）。

### 3 秒自查

下次再遇到，看编辑器里那几行长得**跟周围不一样**：周围是「锁定:真」「自动触发:真」，而它是 `isLocked:true`——一眼就能认出来，这种行保存必坏。

## 修复后会怎样

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 中文视图里粘贴 `isLocked:true` 后保存 | 落盘 `isLocked:真` ❌ | 落盘 `isLocked:true` ✅ |
| 中文视图里粘贴 `movementType:LAND` | 落盘 `movementType:陆地` ❌ | 落盘 `movementType:LAND` ✅ |
| 中文视图里粘贴 `movementType:LAND,WATER` | 落盘 `陆地, 水面` ❌ | 落盘 `LAND, WATER` ✅ |
| 正常打开 → 保存（原有内容） | `真` → `true` ✅ | `真` → `true` ✅ 不变 |
| 中文值反译（`水面` → `WATER`） | 正常 ✅ | 正常 ✅ 不变 |
| 英→中方向（切中文视图） | 正常 ✅ | 正常 ✅ 不变 |

**核心原则**：已经是英文目标值的，原样保留；是中文值的，照旧翻回英文。不新增任何"猜测"逻辑。

## 怎么改

把「特殊值」那一处判断加上方向条件——**只有「英→中」才查表转换，「中→英」遇到英文值直接放行**。

- 改动量：**一行**
- 不动：翻译主流程、词库内容、屏蔽词、行尾灯泡、缓存
- 副作用：无。这是纠正一处方向搞反的判断，不是加兜底

# 问题二：中文「真」在某些位置翻不回英文

## 为什么会这样

「真」「假」这两个字没登记在**主词表**上（主词表管「锁定」「攻击力」这类词，句子里出现就能认）。它们被单独归在**值专用小表**里，那张表只能整格对照，不参与句子里的逐个识别。

引擎为了补这个缺口，专门写了一条补漏规则，但把适用范围定得太窄：**只认「紧跟在等号/逗号/左括号之后」并且「后面紧挨逗号/右括号/右花括号」的写法**。

所以：整格写「真」→ 认；括号参数里（`空的=真`）→ 认；**其他位置 → 不认，原样留下**。

## 修复前的表现

| 文件里的写法 | 保存后落盘 |
|---|---|
| `自动触发:真`、`显示为整数:假` | `true` / `false` ✅ |
| `空的=真`、`func(真)`、`真,假` | `true` ✅ |
| `if 真`、`not 真`、`真 and 假`、`真 且 假` | 还是「真」❌ |
| `%{真}`、`%{if 真}`、`%{真 and 假}` | 还是「真」❌ |
| `[真]`、`{真}`、`真;假`、`真\|假`、`真/假`、`真-假` | 还是「真」❌ |
| `真=>1`、`真<1`、`真==假` | 还是「真」❌ |
| `真，假`（全角逗号）、`真（假）`（全角括号） | 还是「真」❌ |
| `func(需要=真) and 假` | 括号里翻成 `true`，`and 假` 漏 ❌ |

反方向（英→中）同一个毛病：`if true`、`[true]`、`true and false` 切中文视图时不会变成「真」。

**你这次没踩到这条**——你那份文件里没有这类写法，所以这次保存历史里看不到它。但它真实存在。

## 修复后会怎样

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `if 真` / `not 真` | 不翻 | `if true` / `not true` |
| `真 and 假` / `真 且 假` | 不翻 | `true and false` / `true 且 false` |
| `%{真}` / `[真]` / `{真}` | 不翻 | `%{true}` / `[true]` / `{true}` |
| `真=>1` / `真;假` / `真，假` | 不翻 | 全部翻掉 |
| `func(需要=真) and 假` | 只翻一半 | 全翻 |
| `真值` / `测试真` / `真假` / `真的很强` | 不动 | **仍然不动**（前后是汉字，算词的一部分） |
| `isTrue` / `trueFlag` / `truthy` | 不动 | **仍然不动**（前后是字母，算词的一部分） |

额外的：值末尾粘了看不见的字符（复制粘贴/输入法带进来的零宽空格、BOM）时，连「整格是真」都认不出——这次一并清掉。

## 怎么改（**未实施，方案待批**）

把识别标准从「只认那几个标点」改成「认它是不是一个独立的词」：前后挨着汉字、字母、数字就算词的一部分，前后是空格、运算符、各种括号、全角标点就当作独立值翻掉。两个方向一起改。

- 改动量：两条识别规则 + 引号区间跳过 + 值两端不可见字符清理
- 不动：翻译主流程、词库内容、屏蔽词、灯泡逻辑
- 唯一行为变化：以前漏的位置现在会翻，没有倒退

# 风险与边界（明确不做的事）

| 项 | 为什么不做 |
|---|---|
| 中文句子里的词（成段中文在保存时逐个翻回英文） | 这是另一个层面的问题：中文没有空格分词，现有识别对中文几乎不起作用。改它会让**所有**中文短语在保存时都被尝试翻译，影响面是全局的。单独立项，先想清楚「哪些值该整句翻」 |

| 逗号后空格 | 开着「逗号后自动空格」时，反译会把 `LAND,WATER` 输出成 `LAND, WATER`。这是既有设置行为，不是本次 bug；不想要就关掉那个开关 |

## 问题一：`TranslationEngine.translateSingleValue()`

```kotlin
// app/src/main/java/com/rwmodstudio/core/translation/TranslationEngine.kt 第 581-584 行
// 处理特殊值（在 specialValues 中的英文值，如 LAND, WATER 等）
if (processed in translationDict.getSpecialValues()) {
    return translationDict.getValueTranslationBack(processed)   // ← 不分方向
}
```

**成因链**：

1. `translateKVToEnglish()` → `translateValue(value, enToZh = false)` → `translateSingleValue()`
2. `processed` 是英文 `true`，不在 `ZH_BOOLEANS`（第 577 行只管中文），落到第 581 行
3. `true in specialValues` 成立 → 调 `getValueTranslationBack("true")`
4. 该函数走 `lookupZhValue()`（`TranslationDict.kt` 第 1017 行）：`zhToEn[form] ?: valueTranslations[form]`
5. `valueTranslations` 是**双向写入**的（`loadFromFile()` 第 923-926 行、`parseTranslationText()` 第 808-811 行、`parseUserTranslationJson()` 第 694-696 行，三处一致）：
   `valueTranslations["true"]="真"` 且 `valueTranslations["真"]="true"`
6. 于是查 `valueTranslations["true"]` → `"真"`，反译把英文写成了中文

**修法**：

```kotlin
if (processed in translationDict.getSpecialValues()) {
    // 中→英方向：值本身就是英文目标值，原样保留；否则会被双向值表反查成中文
    return if (enToZh) translationDict.getValueTranslationBack(processed) else processed
}
```

**充分性验证（已跑测试确认）**：

- `valueTranslations` 里的英文 key 共 **9 个**：`true/false/LAND/WATER/HOVER/AIR/OVER_CLIFF/OVER_CLIFF_WATER/NONE`，**全部属于 `specialValues`**（三处解析逻辑都只对 `specialValues` 做双向写入）
- 因此第 581 行是唯一的出口，修它即可全覆盖；第 587 行那个 `if (!enToZh)` 分支对这些值**不可达**（581 先 return），对普通英文值（`infoOnlyNoBox`/`0s`/`ROOT:...`）查不到条目 → 原样返回（已实测）
- `translatePercentVariableSingle()`（`%{...}`）不含 specialValues 分支，`%{true}` 反向翻译本来就安全

**测试**：

- 在 `TranslationRoundTripTest` 加幂等性断言：对上述 9 个值，`translateToEnglish("k:$v") == "k:$v"`
- 加中文反译不倒退断言：`k:真`→`k:true`、`k:水面`→`k:WATER`

**上一版报告的一处更正**：「取消行尾灯泡会触发本 bug」是错的。`onLightbulbToggle`（`EditorScreen.kt` 第 1368-1388 行）熄灭时恢复的是 `lineOriginalTexts[line]`，即点亮前的**中文视图行**，不是英文原文。真正会引入英文的路径：粘贴、英文输入法手打、`SearchTranslationCache.getChineseContent()` 的兜底返回值（引擎 `awaitReady()` 失败返回原文，见第 255-257 行；`translateToChinese` 抛异常返回原文，见第 262-264 行，此时编辑器仍按 `isEnglish=true / showChinese=true` 处理，保存即整篇反译）、外部文本替换。

## 问题二：两条布尔 token 正则

```kotlin
// TranslationEngine.kt 第 29 / 32 行
private val ZH_BOOL_TOKEN_REGEX = Regex("""(?<=[=,\(])\s*(真|假)\s*(?=[,\)\}])""")
private val EN_BOOL_TOKEN_REGEX = Regex("""(?<=[=,\(])\s*(true|false)\s*(?=[,\)\}])""", RegexOption.IGNORE_CASE)
```

改为「独立词」边界（`\p{L}` 含汉字 `Lo`，`真值`/`真假`/`isTrue` 不会误伤）：

```kotlin
private val ZH_BOOL_TOKEN_REGEX = Regex("""(?<![\p{L}\p{N}_])(真|假)(?![\p{L}\p{N}_])""")
private val EN_BOOL_TOKEN_REGEX = Regex("""(?<![\p{L}\p{N}_])(true|false)(?![\p{L}\p{N}_])""", RegexOption.IGNORE_CASE)
```

- 调用点：`translatePercentVariableSingle()`（第 507-515 行）、`translateSingleValue()`（第 604-612 行）；`%{...}` 内层与外层各跑一次替换，幂等
- 引号区间跳过：替换前对 `"..."` / `'...'` 做区间标记（就地扫描，**不要**复用 `blockQuotedDictWords` 的用户开关语义），保证 `k:"真"` 行为不变
- 零宽字符：`translateKVToEnglish` / `translateKVToChinese` 取 `cleanValue` 处，在 `#` 注释切分**之后**执行
  `trim { it.isWhitespace() || it.code in 0x200B..0x200D || it.code == 0x2060 || it.code == 0xFEFF || it.code == 0x00A0 }`
- 不要动 `TranslationDict.compilePatterns()` 的 `\b(...)\b`——那是「中文句子里的词」这一独立问题（见风险与边界），改它需要连带评估所有中→英文本翻译

**测试**：新增 `TranslationBoolTokenTest`，复用 `TranslationRoundTripTest` 的 `loadFromFile` 反射加载方式。
