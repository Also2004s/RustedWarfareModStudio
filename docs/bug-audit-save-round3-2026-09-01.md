# 一、🔴 高危（3 条）

### 1. 配置导入会写坏用户数据
- **为什么**：导入本地配置 zip 时，用户翻译表/补全表等文件用普通复制（copyTo）直接覆盖目标文件，不是"临时文件+改名"的原子写。覆盖写到一半进程被杀 → 文件损坏 → 下次启动解析失败按空表处理 → 你手动加的翻译、自定义补全全"消失"。
- **改之前**：导入配置时被杀/闪退 → 翻译表和补全表可能损坏 → 重启后内容丢了。
- **改之后（建议）**：导入落盘改原子写（.tmp+rename）→ 写一半被杀时旧文件完好，最多导入失败，不损坏已有数据。

### 2. 编辑后立刻退后台，修改可能丢
- **为什么**：退后台（按 Home）时的自动保存是"后台启动协程"——不等写盘完成就返回。如果按 Home 后进程马上被杀（内存紧张/用户清后台），保存协程没跑完 → 最后一次编辑丢失。
- **改之前**：编辑几行 → 立刻按 Home → 被杀 → 打开发现刚才改的没了。
- **改之后（建议，注意副作用）**：**不能改成主线程同步等待写盘**——ON_PAUSE 是主线程回调，同步等 IO 会造成 ANR（当初注释就明确为避 ANR 才非阻塞）。可行方向：① 保持非阻塞，保存协程用 SupervisorJob 确保启动后尽力完成（现状已近似）；② 加"未完成写盘标记"，下次启动检测到该文件有未落盘修改时提示恢复；③ 权衡后接受小窗口（进程被杀本就是罕见场景）。

### 3. 兜底保存失败，用户完全不知道
- **为什么**：编辑器实例销毁时的兜底落盘（onDisposeFlush）是"后台启动 + 失败只打日志"，不检查结果、不提示。多实例并存时（最多 5 个），保存并退出/切页时其它实例全靠这个兜底——它失败了你还以为保存好了。
- **改之前**：保存并退出后，某个文件实际没写成功，但界面一切正常，无任何提示。
- **改之后（建议）**：兜底落盘失败时提示"部分文件保存失败"，或保存并退出时对每个实例确认落盘结果。

# 二、🟡 中危（5 条）

### 4. 保存并退出：多个文件时可能走"兜底"而非"正常保存"
- **为什么**：保存并退出时每个实例各自保存，**第一个**保存完就触发"销毁全部实例"——其余实例的保存协程可能还没跑完就被取消，只能靠兜底落盘（见第 3 条）。文件多/文件大时更明显。
- **改之前**：同时编辑 3 个文件点保存并退出，2 个走了兜底路径，若兜底失败即丢。
- **改之后（建议）**：等全部实例保存完成再统一退出（统计所有实例的保存结果）。

### 5. 历史"回退修改"和编辑器内容打架
- **为什么**：回退修改会把文件写回旧版本，但如果这个文件**还在编辑器里开着**（有未保存的新内容），回退写盘和编辑器自动保存会互相覆盖——结果取决于谁后写，可能把新内容覆盖成旧版。
- **改之前**：编辑器开着文件 A → 在历史里对 A 点回退 → 编辑器里的新内容可能被回退成旧版，或回退被自动保存覆盖无效。
- **改之后（建议）**：回退前检查文件是否在编辑器打开且有未保存修改，是则提示先保存/关闭，或回退后同步刷新编辑器。

### 6. 危险行为"确认记录"并发会丢
- **为什么**：危险行为确认（markVerified）是"读整个文件 → 加一条 → 整个写回"，无锁。用户快速连续触发两个危险操作（如批量删除）时，两个确认同时读同一旧数据 → 后写覆盖先写 → 丢一条确认 → 下次同样操作又要确认一次。
- **改之前**：连续确认两个危险操作，其中一个确认丢失，下次还要再确认。
- **改之后（建议）**：确认操作加锁串行，或确认标记改原子追加。

### 7. 翻译库单条编辑的文件写入无锁
- **为什么**：翻译库"新增/修改单条"分两步：先读整个文件 → 改 → 写回（文件 IO 部分无锁，只有内存字典有锁）。两个地方同时编辑翻译库（如翻译页和编辑器同时保存条目）→ 丢一条。
- **改之前**：翻译页和编辑器同时改翻译条目，其中一条被覆盖丢。
- **改之后（建议）**：翻译库文件读改写统一加锁（复用内存字典那把锁）。

### 8. 更新包下载并发会写坏
- **为什么**：下载的临时文件是固定名字且无锁。重复触发下载（触发面窄）时两个下载写同一临时文件 → 互相截断 → 下载的 APK 损坏、安装失败。
- **改之前**：极端情况下重复点下载 → APK 损坏装不上。
- **改之后（建议）**：下载去重（已有 state 判断，补一层锁即可），或临时文件名加唯一后缀。

# 三、🟢 低危（4 条）

### 9. 待办保存失败无提示
- **为什么**：待办保存失败只打日志，用户不知道。勾选/删除后被杀 → 操作丢失且无感。
- **改之后（建议）**：失败时 Toast 提示。

### 10. 翻译缓存索引偶发漏存（可自愈）
- **为什么**：索引保存和"写入新缓存记录"有极小竞态窗口，索引可能漏掉刚写的条目 → 下次启动重新翻译该文件（性能损失，内容不丢）。
- **改之后（建议）**：保存索引和标记脏位合并成同一临界区。

### 11. 设置写盘失败无感知
- **为什么**：设置保存是异步的（与系统设置一致），失败仅日志。磁盘异常时改的设置重启回默认。
- **改之后（建议）**：低频场景，可接受；如需可在下次启动检测设置文件损坏并提示。

### 12. 调试开关"退后台保存"关闭后静默
- **为什么**：`devSaveOnPause` 是调试开关（默认开）。若被关闭，即使自动保存开着，退后台也不保存——开发调试时容易关掉忘了开。
- **改之后（建议）**：该开关从开发页隐藏或默认保持开，避免误关。

# 四、已确认安全 / 设计行为（不是问题）

- **关闭自动保存后不保存**：设计行为（自动保存关闭 = 手动保存），不算隐患。
- **退后台保存默认开启**：`devSaveOnPause` 默认 true，正常使用不会裸奔。
- **编辑器主保存（saveSync）**：原子写 + 文本来源正确 + 路径校验，已核实无问题。
- **保存历史 / 验证码 / 翻译缓存写盘**：均已是原子写 + 加锁（前两轮修复），无新增隐患。

# 补充：多线程失效修复记录（2026-09-01，老板实测确认后回退）

## 🔴 高｜多线程（查重 / 翻译缓存 / 继承缓存 全失效）

- **为什么**：修复过程中的两个错误——①把「可再生的缓存/输出文件」（查重输出、翻译缓存、继承缓存）也改成了**原子写**（写 tmp + rename + per-path 锁），高频写盘时开销巨大，把多线程加速完全抵消；②在**热路径**上加了锁（进度管理器每文件 update、缓存新鲜度判定每文件调用）。
- **改之前**：多线程开关开了也和关了一样慢（热路径全是锁和原子写，实际串行）。
- **改之后（6 处回退，编译 + 220 单测通过）**：
  1. 查重输出 / 翻译缓存 / 继承缓存：`atomicWriteText` → `writeText`（直接写，无锁）
  2. TaskProgressManager：去掉 `synchronized(lock)`（每文件 update 不再撞锁）
  3. SearchTranslationCache / InheritanceCache：删除 `currentLibVersionValue()` TTL 锁，`isFresh` 直接读 `@Volatile` 字段（会话内恒定）
  4. **保留**：缓存索引原子写（低频防撕裂）、用户数据原子写（保存/设置/历史/待办）
- **原则（已入长期笔记）**：原子写只用于「不可再生的用户数据」；「可再生的缓存/输出」用直接写。判断标准 = 数据能否再生。

## 查重速度修复（结构性优化，2026-09-01）

- **为什么**：缓存预热是**整文件翻译一次**；查重是**每行调 `translateToEnglish`**——每次重复走完整 processLines 状态机的固定开销（List 创建/joinToString/正则对象），大文件几百行 = 几百次固定开销。多线程只能并行文件级，救不了每行重复开销（所以"开关开了也没用"）。
- **改之前**：查重逐行调用翻译引擎，比缓存预热慢一个量级。
- **改之后**：查重改为**整文件翻译一次**（`translateToEnglish(content)`），按行索引对齐对比（`processLines` 保持行数，多行字符串按原始行还原）。性能提升一个量级，多行字符串处理比逐行更准。编译 + 220 单测通过。
