# 效果版（用户视角：为什么 / 改之前 / 改之后）

## 🔴 会让你白干 / 丢东西 / 用不了

### ★ 撤销 / 重做按钮的"亮灰"是错乱的（核心问题，已修）
- **为什么**：编辑器内部有两份东西 —— "内容"和"操作历史记录"。**撤销 / 重做的时候，它是先把内容改掉、再去移动历史记录里的指针**。而 App 是**在"内容刚改完"的那一瞬间**去问"还能不能撤销"的 —— 这时候指针还没动，**问到的永远是改动之前的答案**。
- **改之前**：一路按撤销，**按钮一直亮着**（每次都被告知"还有更多可以撤"），一直撤到最底了**还是亮的**；这时候按一次重做，反而被告知"已经撤到底了、没得撤了"，**撤销按钮一下子变灰**。给人的感觉就是"撤销和重做的状态是反的、乱的"，完全没法根据按钮判断到底还能不能撤。
- **改之后**：撤销和重做时，等指针移动完（下一帧）再问一次，按钮亮灰与真实状态一致 —— 撤到底就灭，有得撤就亮；重做之后撤销按钮立刻恢复亮。
- **影响面**：顶部撤销按钮、底部符号栏的重做按钮，**两者的亮灰都受此影响**（读的是同一份状态）。

### 1. 切换中英之后，撤销历史全部消失
- **为什么**：编辑器切换中英显示时，是把**整篇内容重新灌一遍**（不是在原文上逐字换）。而编辑器的"操作历史"是跟着这份内容走的 —— 灌新内容等于换了一本新记事本，**旧本子上的历史自然全没了**。→ **触发**：在「更多」菜单里点过「切换为中文 / 英文」。
- **改之前**：编辑了半天 → 点一下切换中英 → **撤销按钮直接变灰**，之前几十步操作一步也撤不回来。
- **改之后**：切换中英这个动作本身也算一步，能撤销；切换之前的历史也留着，可以一路往回撤。

### 2. 全部撤销回原样，但「未保存」标记不熄灭
- **为什么**：编辑器内核**没有**「现在的内容跟存盘内容是否一致」这个标记，是 App 自己记的一面小旗子「改过没有」。问题在于这面旗子**只会被立起来、不会被放倒**（唯一放倒的时机是"保存成功"）。→ **触发**：随便改几个字，再一路撤销回原样。
- **改之前**：内容已经和存盘的一模一样了，但**顶部保存按钮一直亮着**；返回时还问你"要保存吗"；自动保存开着的话，还会把这份"没变化"的内容再存一次。
- **改之后**：撤销回到存盘时的样子，保存按钮自己熄灭，返回不再多问，也不会触发多余的自动保存。

### 3. 行尾灯泡翻译后撤销，灯泡和内容对不上
- **为什么**：行尾灯泡「点亮 / 熄灭」是 App 自己记的一份名单，而撤销只改编辑器里的正文。两份东西**各记各的**，一撤销就对不上。→ **触发**：点亮某行（把英文翻成中文）→ 再撤销。
- **改之前**：那行内容已经变回英文了，但**灯泡还亮着**；此时再点一次灯泡，它以为自己该"恢复原文"，结果把内容弄得更乱。
- **改之后**：撤销后灯泡状态跟着刷新，亮着的行就是真的被翻过的行。

## 🟡 状态不对（点得动，但结果是错的）

### 4. 切回已经打开的文件，撤销按钮显示的是上一个文件的状态
- **为什么**：同时打开多个文件时，每个文件各自记着自己"能不能撤销"，但顶部那个按钮只有一份。**切回来的时候，没人把当前文件的状态重新告诉按钮**，它就还停在刚离开那个文件的状态上。→ **触发**：文件 A 改过（按钮亮）→ 切到没改过的文件 B（按钮变灰）→ 再切回 A。
- **改之前**：切回 A 之后**撤销按钮还是灰的**，明明能撤销却点不动，得先在 A 里随便改一个字它才"活"过来。
- **改之后**：切到哪个文件，按钮就显示哪个文件的真实状态。

### 5. 坐标可视化回写代码后，撤销历史被清空
- **为什么**：同第 1 条 —— 工具是把**整篇内容换掉**再写回编辑器的。
- **改之前**：用坐标可视化工具算完写回代码，之前的撤销历史没了。
- **改之后**：跟第 1 条一起改就能保留历史；也可以维持现状（毕竟整篇是被工具重写的，重写前的历史参考价值有限）。**建议一起改**，实现成本一样。

## 🟢 内核固有限制（建议维持现状）

### 6. 改动特别多之后，最早的操作撤不回来
- **为什么**：编辑器内核默认只保留最近 **500 步**操作，超出的自动丢弃最老的（这是为了防止长文档把内存吃爆）。
- **改之前**：在几万字的大文件里连续改了几百上千处，想撤销到很早以前 → 撤到某一处就再也撤不动了（按钮变灰）。
- **改之后**：建议维持现状（500 步写 mod 足够）；真要调大可以改，但会多占内存，且极端情况下有卡顿风险。

## 第二轮追加（实例生命周期 / 搜索替换 / 撤销粒度）

### 7. 去设置页转一圈回来，撤销历史全没了
- **为什么**：编辑器和设置页是**两个互斥的页面**，离开编辑器时那个文件的编辑窗口会被**整个关掉**（不是最小化）。为了让你回来还能看到原内容，App 把内容存了一份缓存，回来时**重新灌一份新的进新窗口** —— 而操作历史是跟着窗口走的，新窗口的历史自然是空的。→ **触发**：在编辑器里改过东西 → 去设置 / 翻译库 / 自定义补全 / 项目视图 / 待办 等**任何一页** → 再回编辑器。
- **改之前**：去设置页看一眼回来，撤销按钮已经灰了，刚才几十步操作一步也撤不回来（**内容还在**，只是历史没了）。
- **改之后**：离开再回来，撤销历史照旧可用。
- **补充**：在编辑器里**切换文件标签**（不离开编辑器页）不会踩这个坑 —— 每个文件各有自己的实例并且一直保留着。所以它**只在"跨页面"时触发**，不留意很难联想到原因。

### 8. 用查找替换批量改完，撤销历史被清空，且替换本身撤不回来
- **为什么**：查找替换是"先直接改磁盘上的文件，再让编辑器重新读一遍"。重新读 = 换一份新内容进窗口（同第 7 条），历史随之清空。→ **触发**：用查找替换做一次批量替换。
- **改之前**：批量替换完，撤销按钮变灰 —— **替换这个动作本身也撤不回来**，改错了只能再替换回去。
- **改之后**：替换作为一步正常操作进入历史，撤销可以退回替换前。

### 9. 撤销一次，退回的是好几秒前
- **为什么**：编辑器内核会把**连续输入**合并成一步（避免你敲 20 个字要撤销 20 次）。合并窗口默认是 **8 秒** —— 也就是 8 秒内敲的字算一步。→ **触发**：正常速度连续打字，然后按撤销。
- **改之前**：明明只打了一小段，按一下撤销**整段一起消失**，很难精确退到想退的位置。
- **改之后**：把合并窗口调小（例如 1～2 秒），撤销粒度接近主流编辑器的手感。

### 10. 同时打开超过 5 个文件时，最早那个文件的撤销历史会丢
- **为什么**：App 为了控内存，最多同时保留 5 个文件的编辑窗口，开第 6 个时最早那个被关掉（内容会先存好）。窗口关了，它的历史也就没了。→ **触发**：一次开 6 个以上文件，再切回最早的那个。
- **改之前**：切回最早打开的文件，撤销按钮是灰的。
- **改之后**：建议维持现状（这是内存保护）；若经常需要跨很多文件撤销，可把上限调大一点。

### 11. 极快地连点两下撤销，可能只生效一次
- **为什么**：撤销按钮是用"计数 + 监听变化"的方式通知编辑器的，两下点击如果落在同一帧里，计数会从 0 直接跳到 2，编辑器只看到"变了"，于是只撤销一次。→ **触发**：手指极快连点（或大文件卡顿时连点）。
- **改之前**：连点两下只退一步（正常速度点不会遇到）。
- **改之后**：改成"事件队列"式通知，点几下退几步，不丢。

## 关键钩子（修复 #2 #3 的前提）

`io.github.rosemoe.sora.event.ContentChangeEvent` 自带 **`isCausedByUndoManager()`**，可精确区分「撤销/重做引起的变更」与「用户打字/程序改文本」。

**全仓 grep 确认项目从未使用过它**（`grep -rn "isCausedByUndoManager" app/src/main/java/` 为空）——
这正是 #2 #3 一直修不掉的症结：没有这个信号，就无法在"撤销落定"这一刻做状态校正。

```java
// ContentChangeEvent 结构（javap 核实）
public static final int ACTION_SET_NEW_TEXT = 1;
public static final int ACTION_INSERT = 2;
public static final int ACTION_DELETE = 3;
public boolean isCausedByUndoManager();
```

## 各条细节

### #1 / #5 撤销栈为什么被清空

- 清栈路径（`grep -n "resetTextRequest" EditorScreen.kt`）共 6 处赋值：
  - `851 / 928 / 934` —— 文件加载 / 加载失败：**合理**，换文件本就该换历史
  - `1483 / 1592` —— 「切换为中文 / 英文」：**不合理**，用户只是换了显示语言
  - `496` —— `externalReplaceTick`（坐标可视化回写）：整篇被工具重写，按 #1 一起改
- 底层依据：`CodeEditor.setText(CharSequence, boolean, Bundle)` 的字节码里是
  `invokespecial Content."<init>"` + `Content.setUndoEnabled(Z)` + `EditorStyleDelegate.reset()` +
  `EditorTouchEventHandler.reset()` —— 即**新建了一个 Content 对象**，而 `UndoManager` 是 `Content` 的成员
  （`private UndoManager undoManager`），随旧对象一起被丢弃。
- 修法：把「切语言」的整篇替换从 `setText` 改为
  `editor.text.replace(0, editor.text.length, translated)`（Content 直接改，**会进撤销栈**），
  同时保留原有的 `latestEditorText` / `text` / `resetTextRequest` 同步逻辑。
  ⚠️ 风险点：`setText` 额外做了 listener 重挂、语言分析重置、触摸/样式重置，改走 `replace` 后需实测
  高亮、补全、光标与滚动是否正常（建议先只改「切语言」一处，验证后再推广到 #5）。

### #2 为什么不能用 `editor.text` 的某个 API 直接判断

- `javap io.github.rosemoe.sora.text.Content`：只有 `canUndo` / `canRedo` / `undo` / `redo` /
  `getUndoManager` 等，**没有** `isModified` / `markSaved`。
- `javap io.github.rosemoe.sora.text.UndoManager`：`actionStack` / `stackPointer` / `maxStackSize` /
  `isModifyingContent` 等，同样**没有**保存点标记。
- 因此只能在项目侧维护快照：
  ```kotlin
  var savedSnapshot by remember(filePath) { mutableStateOf<String?>(null) }
  // 保存成功后：savedSnapshot = latestEditorText
  // ContentChangeEvent 里：
  if (event.isCausedByUndoManager) {
      isModified = (cachedText != savedSnapshot)
      // #3：同步重建灯泡状态
  }
  ```
  ⚠️ 只在 `isCausedByUndoManager` 分支做字符串比较 —— 打字热路径**不能**加 O(n) 比较。

### #3 灯泡状态怎么重建

- 现状：`onLightbulbToggle`（`EditorScreen` 内）点亮时把原文存进 `lineOriginalTexts`，取消时用它恢复。
- 撤销后两者脱钩：内容回退了，`litLines` / `lineOriginalTexts` 没回退。
- 最小修法：撤销/重做事件里 **清空** `litLines` + `lineOriginalTexts`（灯泡全灭，用户按需重新点）；
  更精细的做法是按当前内容重新校验每行是否仍是译文（成本高，收益有限，不建议首版就做）。

### #4 修法与注意

- `MainApp.kt` 现在的回调是
  `onCanUndoChange = { if (path == activePath) editorCanUndo = it }`，
  它只在**该实例内部** canUndo 变化时触发；多实例下 `active` 从 false 变 true 时没有触发源。
- 在 `EditorScreen` 加：
  ```kotlin
  LaunchedEffect(active, canUndo) {
      if (active) onCanUndoChange?.invoke(canUndo)
  }
  ```
  既覆盖"切回前台"，也覆盖"当前文件 canUndo 变化"。

### #6 补充

- `setText` 会把 `undoEnabled` 按 `isUndoEnabled()` 重新设到新 Content 上，所以**加载文件后撤销功能是开的**，
  只是栈是空的 —— 表现就是"新打开的文件撤销按钮变灰"，属正常。
- 若将来允许调 `maxUndoStackSize`，注意它与长文档内存占用正相关，别设成无限。

### #7 跨页面往返为什么必然丢栈（本轮最需要先确认的一条）

- 渲染位置：`MainApp.kt:1045` 的 `Screen.EDITOR -> { ... openPaths.forEach { key(path) { EditorScreen(...) } } }`
  位于 `when (currentScreen)` **内部** —— 切页即从组合中移除，所有 EditorScreen 实例（连同编辑器 View）销毁。
- 回来时 `openPaths` 由 MainApp 持有（不丢），所以文件"看起来还开着"，但**实例是全新的**；
  文本从 `workspaceEntry`（workspace 缓存）恢复，恢复路径末尾即为
  `resetTextTick++; resetTextRequest = text to resetTextTick`（`EditorScreen.kt:850-851`）→ `setText` → 清栈。
- 为什么不能"顺手保留"：`UndoManager` 是 `Content` 的成员，`Content` 又是编辑器 View 的成员 —— View 一销毁整条链都没了。
  要跨页面保留历史，只能把 `Content`（或 `UndoManager`，它实现了 `Parcelable`）**序列化存起来**，
  回来时用 `setUndoManager(...)` 还原。这是**有成本的改动**（要处理内存占用、有效期、多文件），需单独评估。
- ⚠️ 这条与 #1 的表现一样（按钮变灰），但**触发路径完全不同** —— 修 #1 不会顺带修好它，别合并处理。
- ⚠️ `WorkspaceEntry` 只存 text / 光标 / 滚动 / 灯泡等，**不含撤销栈**，所以缓存机制也救不了它。

### #8 查找替换为什么也是清栈

- `MainApp.kt` 三处 `searchModifyTicks = searchModifyTicks + paths.associateWith { ... + 1 }`
  （`:1039`、`:1443`、`:1498`，对应不同替换入口）→ 该文件的 `externalModifyTick` 自增
  → `EditorScreen.kt:815` 的 `LaunchedEffect(filePath, externalModifyTick)` 重新从盘加载 → `setText`。
- 设计初衷：替换是**先落盘再重载**，保证编辑器与磁盘一致（避免缓冲区把替换结果覆盖掉）。
  代价是替换不进撤销栈、且清掉已有历史。
- 若要改：替换改为在编辑器缓冲区内直接执行（走 `editor.text.replace` 批量），替换后再落盘 ——
  ⚠️ 需与"搜索替换"面板既有写盘逻辑、`SaveHistoryManager` 记录顺序一起梳理，改动面较大。

### #9 撤销粒度（改起来最省事的一条）

- `javap` 核实：`UndoManager` 静态初始化 `sMergeTimeLimit = 8000L`（8 秒）；全仓无
  `setMergeTimeLimit` / `setMaxUndoStackSize` 调用。
- 修法：编辑器初始化时调一次即可（**静态字段，全局生效**）：
  `io.github.rosemoe.sora.text.UndoManager.setMergeTimeLimit(1500L)`
- ⚠️ 调太小会变成"逐字撤销"（敲一句要撤很多次）；1～2 秒是主流编辑器区间，改完要真机试手感。

### #10 逐出实例

- `MainApp.kt:1050-1058`：`openPaths.size > 5` → `openPaths.drop(1)`，最旧实例 `onDispose` 落盘。
- 逐出即销毁 → 栈丢失，且 `workspace` 缓存里也没有历史（见 #7 最后一条）。
- 维持现状的理由：5 个编辑器实例 + 全部撤销栈常驻内存代价过高；当前已有落盘保护"内容不丢"。

### #11 连点丢事件的机制

- 现状：`MainApp` 的 `editorUndoTrigger++`（Compose State）→ 传参 `undoTrigger` → `EditorScreen` 的
  `LaunchedEffect(undoTrigger)` 响应后 `onUndoTriggerConsumed()` 清零。
- 同帧两次自增 → State 直接 0→2 → `LaunchedEffect` 的 key 只变一次 → 协程只跑一次 → 少撤一步。
- 修法：把"用户意图"从**状态**改成**事件**（`Channel<Unit>(UNLIMITED)` 或 `MutableSharedFlow.tryEmit`），
  接收端逐条消费。⚠️ 同时要拆掉 `onUndoTriggerConsumed` 清零那一路，别留双通道。

### ★ 根因细节（javap 反编译核实，最该留痕的一条）

**sora `UndoManager.undo(Content)` 的字节码执行顺序**：

```
 1: invokevirtual canUndo()Z
 8: invokevirtual isModifyingContent()Z
16: putfield      ignoreModification:Z     // 暂停记录
29: actionStack.get(stackPointer)          // 取待撤销的动作
40: ContentAction.undo(content)            // ★ 应用内容变更 → 触发 Content 通知 → 派发 ContentChangeEvent
45: getfield      stackPointer:I           // ★ 读旧指针
50: putfield      stackPointer:I           // ★ 到这里才写回（慢了一步）
55: putfield      ignoreModification:Z
```

`redo()` 完全同构（`ContentAction.redo(content)` 之后才 `stackPointer++`）。

**为什么普通打字不受影响**：`Content` 对插入 / 删除的通知顺序恰好**相反** ——
`UndoManager.afterInsert/afterDelete(...)`（更新栈指针）**先**执行，之后才遍历 `ContentListener`
派发 `ContentChangeEvent`。所以只有 `isCausedByUndoManager` 这一支需要延后读。

**项目侧还有第二层放大**：`EditorScreen` 的 `EditorToolbarAction.REDO` 分支原本在 `editor.redo()` 之后
立即 `canUndo = editor.canUndo()` —— 这次读其实是**对的**（redo 已返回），但它只改了 `EditorScreen`
的**局部状态、没有上报宿主**（没调 `onCanUndoChange`），而事件回调那次错误上报（false）已经把宿主的
`editorCanUndo` 写成 false 了 → 顶部按钮灰。**两层叠加，才是"点一次重做就灰"的完整成因。**

**为什么用 `post{}` 而不是"读两次"**：`post` 保证在栈指针写回**之后**执行，并与 Compose 下一帧对齐；
且只有撤销 / 重做分支才走这条路，**打字热路径零额外开销**。
